The Administration area is capability-gated and appears in the sidebar's "Your workspace" group.

Only sections allowed by your organisation capabilities are shown.

For a practical setup sequence, use [Workspace Setup For Admins](/docs/using-orcai/workspace-setup).

## Sections

Current administration sections in the app:

- Users (`/app/users`)
- Groups (`/app/groups`)
- Quotas (`/app/quotas`)
- Providers (`/app/providers`)
- Models (`/app/models`)
- Organisation (`/app/organization`)

Which roles see which section is listed in
[Access Control](/docs/using-orcai/access-control#organisation-roles).

Instance-wide actions live in the separate Instance management area,
described below. They are not part of the active organisation's Administration
navigation.

## Users

Users (`/app/users`) is a paginated data table with search over name and email, sorting, and
table actions. It is scoped to the active organisation and acts on
memberships: the row menu and the bulk action remove a user from the
organisation, and the user page changes the organisation role or removes the
membership. The account itself survives and can be invited back. Banning an
account and deleting it live under Manage instance > Users.

Primary actions:

- **Invite user** (`/app/users/add`)
- **View invitations** (`/app/users/invites`)
- **Remove from organisation** in a row menu, and **Remove selected from
  organisation** for the selected rows

Invitation management has its own table page with export and actions. It
lists every invitation of the active organisation, including those other
administrators and managers sent. The invitation form and the table are
described under [Invitations](/docs/using-orcai/access-control#invitations).

**Edit user** opens a user's page at `/app/users/<user id>/edit`. It shows:

- **User information**: name, email, status, email verification and dates.
- **Effective resource access**: every bot, block and asset the user can reach
  in this organisation, with the role and where the access comes from: a direct
  grant, a group, All members, an inherited bot or block, the organisation, or
  public visibility. Use it to answer why someone can or cannot see something.
- **User management**: **Send password reset**, **Send verification email**
  while the address is unverified, the organisation role, and **Remove from
  organisation**.

Admins are protected: only an Admin can give the Admin role, change an Admin's
role or remove an Admin, so a manager sees an Admin's page without the password
reset, the role change or the removal. An organisation keeps at least one
Admin who can sign in: the last one cannot be demoted, removed, banned or
deleted, and a banned Admin does not count. Your own page offers no password
reset and no removal.

Removing a user from an organisation clears that organisation from the user's
open sessions, and entering the app rechecks that the membership still exists.

## Groups

Groups (`/app/groups`) supports:

- Search
- Create custom groups
- Edit and delete custom groups
- Member management with explicit/implicit labels

System groups are immutable. A group opens at `/app/groups/<group id>`;
[Access Control](/docs/using-orcai/access-control#groups) covers the All
Members group and who may see what.

## Quotas

Quotas are managed through quota pools. A pool bounds how much one provider,
or one of its models, may be used in a period.

Quotas (`/app/quotas`) lists the pools with their period, budget, consumed and
remaining amounts. **Add pool** opens `/app/quotas/add` with these fields:

- **Name**, shown to users as the pool their usage is charged to, and an
  optional description.
- **Provider**: the pool meters this provider in its metering mode, tokens or
  requests.
- **Model scope**: "All models from this provider", or one model.
- **Period**: Weekly, Monthly or Yearly. The budget resets in UTC: weekly on
  Monday, monthly on the 1st, yearly on 1 January. Each period starts with the
  full budget; unused budget does not roll over.
- **Budget**: the maximum tokens or requests per period.
- **Priority**: when more than one pool could apply, the higher priority wins.
- **Default pool**: marks the provider's default pool, shown with a Default
  badge. One active pool per provider without a model scope can carry it.
- **Active**: an inactive pool takes no new usage.
- **Eligible groups**: people in any of these groups can use the pool. A pool
  with no eligible groups covers nobody; choose All Members to cover everyone.

Pools cannot be deleted. **Deactivate pool** stops new usage; usage already in
progress still completes.

For each chat request, OrcAI looks at the active pools of the chat's provider
whose eligible groups include the person. A pool scoped to the chat's model
wins over pools covering all models; among those, the higher priority wins,
then the older pool. If no pool covers someone, they cannot chat with that
provider's models.

Each reply reserves its likely cost before the model runs and is charged what
it used once it ends. With requests metering a reply reserves one request per
step it may take, 25 in chat and 20 in the OrcAI Assistant, or what the pool
has left when that is less. A reply starts while at least one request remains,
gets as many steps as it reserved, and answers on the last of them, so it never
uses more than the pool has. With tokens metering the pool needs the whole
estimate remaining: the prompt plus the chat's max tokens, or 16,384 tokens
when the chat sets none, or the model's max output tokens when that is
smaller.

**View pool** opens `/app/quotas/<pool id>`, with the current period's
budget, consumed, reserved and remaining amounts, **Adjust budget** (raising
the budget frees the remaining allowance straight away), the eligible groups
and the recent usage events. **Edit pool** opens `/app/quotas/<pool id>/edit`.

In chat, users may see remaining quota badges by pool name and metering mode.

The OrcAI Assistant draws on the same pools as chat, through the organisation's assistant model. For a separate assistant budget, create a pool for that model alone and assign it to All Members; a model-specific pool wins over the provider's pools. An exhausted pool blocks the assistant like any chat.

## Providers

Providers represent model backends/endpoints available to OrcAI.

Providers (`/app/providers`) lists them with their status and metering mode.
**Add provider** opens `/app/providers/add` with these fields:

- **Kind**: **OpenAI-compatible** for any endpoint that speaks the OpenAI
  API, or **OpenAI** or **Anthropic** for their official APIs. The kind is
  fixed once the provider exists; to switch kind, create a new provider.
- **Name**, shown to users wherever the provider is named.
- **Endpoint**, only for OpenAI-compatible providers: the base URL of the
  endpoint, including the version path. OpenAI and Anthropic providers have
  no endpoint field and use the official API.
- **API key**, stored encrypted. When editing, leave it blank to keep the stored key.
- **Metering mode**: whether quota counts tokens or requests for this provider.
- **Enabled**: only an enabled provider's models can be used in the organisation.

A provider's page (`/app/providers/<provider id>`) shows its configuration and
connected models, with **Add model** and **Edit provider**
(`/app/providers/<provider id>/edit`). There is no separate connection test;
**Discover models** on the Models page is a quick check that the endpoint and
key work.

Discovery lists the models the provider offers: `/models` of the endpoint for
OpenAI-compatible providers and of OpenAI's API for OpenAI providers, and
Anthropic's Models API for Anthropic providers. It also takes each model's
context window and max output tokens where the provider reports them:
Anthropic's Models API does, and so do OpenAI-compatible servers such as
OpenRouter, Together AI, vLLM and Groq. OpenAI's API reports neither.

With an Anthropic provider, OrcAI marks the system prompt and the conversation
of every request for Anthropic's prompt caching. The steps of an answer that
uses tools, and a next answer within the cache's lifetime of about five minutes,
read what was already sent at Anthropic's reduced cache rate. The Assistant declares all of its tools up front there and
loads more of them through Anthropic's tool search, so loading tools or
approving a plan keeps the cache. Claude models without tool search (Claude 3,
and Claude Opus and Sonnet 4.1 and earlier) get loaded tools added to the request
instead, like other providers. Claude's reasoning, when the model returns any,
shows in the answer's work log as Thinking.

## Models

Models are managed separately from providers and can be filtered by provider.

Current models page (`/app/models`) features:

- Search by model/provider text
- Provider filter
- **Add model** (`/app/models/add`)
- **Discover models**, which lists the models a provider offers, adds the
  new ones and fills in the token limits a known model still lacks

A model has a name, an optional description, a provider, the **Provider model
ID** the endpoint expects, its **Capabilities**, a **Deprecated** flag, and
two token limits, empty when unknown:

- **Context window**: how many tokens the model reads at once. A chat reply
  shows how full it was, and a long chat is summarized once it fills 80% of
  the window after the reply's room, so a smaller value summarizes earlier and
  keeps prompts cheaper. Empty means 128,000. A reply without max tokens asks
  for at most half of it.
- **Max output tokens**: how many tokens the model writes per reply at most. A
  chat's max tokens cannot be set higher, a reply asks for no more, and a
  limit below 16,384 lowers the quota reservation of a chat without max tokens.

Rediscovery never overwrites a limit that is already set, so edited limits
stay. A model opens at `/app/models/<model id>`, and **Edit model** at
`/app/models/<model id>/edit`.

<Callout title="Chat Models" type="info">
	A model appears in chat only with at least the **Text** and **Tool calling** capabilities. Discovered models start with no capabilities, so set them on each model before it can chat.
</Callout>

## Instance management

Instance management is a separate application area under `/instance`, with
its own sidebar and two pages. Instance administrators can open it from the
shared user menu or the organisation picker, including when they have no
organisation memberships. `/instance` opens the Organisations page.

**Organisations** (`/instance/organizations`) lists every organisation of the
instance with its slug and member count, with search, creates one with
**Create organisation**, and deletes one. The creator becomes the first
administrator of what it created.

Deletion is thorough. The dialog first shows an impact preview counting the
memberships, pending invitations and groups that go with the organisation, plus
the resources whose only scope is this organisation, and it enables Delete only
once the organisation's slug is typed back. The delete then removes the
memberships, invitations and groups along with the organisation's authorisation
relationships, and any session that had the organisation active loses it and
lands back on the organisation selection page. Resources scoped only to the
deleted organisation stay with their owners, without an organisation for now.
Its former members lose their direct grants on them, as when they are removed
one by one.

**Users** (`/instance/users`) lists every account of the instance, searchable over name and email,
with the organisations each account belongs to and its role in them. From here
an account is banned, unbanned, or deleted. None of the three applies to your
own account.

The active organisation remains selected while the administrator is in this
area, but it does not scope or otherwise affect either page. The **Back to
app** action returns to `/app`, where the usual active-membership checks
apply.

## The instance administrator

Most administration is scoped to one organisation. A few actions concern the
whole instance and belong to the instance administrator, an account marked with
the instance role in the database. The first account created when an instance is
initialised is an instance administrator.

Only an instance administrator may:

- create an organisation,
- delete an organisation,
- ban and unban an account,
- delete an account,
- list every organisation and every user of the instance.

The instance role grants nothing inside an organisation. An instance
administrator still needs a membership to enter an organisation or manage its
members, and an organisation administrator manages memberships only.

## Organisation

The Organisation page (`/app/organization`) under Administration edits the active organisation's
name, slug and logo and shows its ID and creation date. Only administrators of
the organisation see it. To work on another organisation, switch to it with the
organisation picker first. Creating and deleting an organisation are instance
actions and live under Manage instance > Organisations.

Users switch organisation with **Switch organisation** in the user menu, which
opens `/select-organization`.

### Assistant model

The **Assistant model** picker on the same page chooses the model the
[OrcAI Assistant](/docs/using-orcai/assistant) answers with. It is the chat
model picker, limited to usable models: models with tool calling, not
deprecated, on an enabled provider. **Clear** removes the choice.

While no model is set, the assistant is unavailable to everyone in the
organisation. Deleting the model, or its provider, clears the setting. If the
chosen model later becomes unusable, because it is deprecated, loses tool
calling or its provider is disabled, the setting stays, the page warns with the
reason, and the assistant's replies fail until another model is chosen.

## Operational Guidance

- Configure providers and models before onboarding large user groups.
- Keep quotas aligned with model pricing and expected usage.
- Use groups and grants to avoid manually maintaining per-user permissions.
