OrcAI uses organisation-scoped access control with capability-gated UI and resource-level grants. Authorization is enforced by backend checks and shared capability hooks in the app.

## Access Model Overview

- You sign in as a user account.
- You operate inside one active organisation at a time.
- Sidebar sections and actions are visible only when capability checks pass.
- Many resources (assets, blocks, bots) support direct sharing and group-based grants.

## Organisation Roles

Every membership carries one of four organisation roles. The role decides which
organisation permissions the person holds, and so which sidebar sections and
create actions they see. The role picker lists each role's permissions.

| Permission | Admin | Manager | Member | Viewer |
| --- | --- | --- | --- | --- |
| Read workspace (`read`): the app and the Library | Yes | Yes | Yes | Yes |
| Create bots (`create_bot`) | Yes | Yes | Yes | No |
| Create blocks (`create_block`) | Yes | Yes | Yes | No |
| Create assets (`create_asset`) | Yes | Yes | Yes | No |
| Manage members (`manage_members`): Users | Yes | Yes | No | No |
| Invite members (`invite_members`) | Yes | Yes | No | No |
| Manage groups (`manage_groups`): Groups | Yes | Yes | No | No |
| Manage quotas (`manage_quotas`): Quotas | Yes | No | No | No |
| View analytics (`view_analytics`): Analytics | Yes | No | No | No |
| Manage providers (`manage_providers`): Providers | Yes | No | No | No |
| Manage models (`manage_models`): Models | Yes | No | No | No |
| Manage organisation (`manage_organization`): Organisation | Yes | No | No | No |

Managing administrators also needs `manage_organization`: only an Admin can
invite someone as Admin, give the Admin role, or change or remove an Admin. An
organisation always keeps at least one Admin.

The organisation role covers organisation-wide actions. What someone may do
with a particular bot, block or asset comes from the grants on that resource,
described under [Resource Sharing](#resource-sharing). Every role, Viewer
included, can chat and use the [OrcAI Assistant](/docs/using-orcai/assistant).
The assistant acts with your own permissions and never exceeds them.

## Active Organisation

Signing in activates the user's only organisation automatically. Users with
multiple organisations choose one from the selection page. Pending invitations
keep that picker visible even when one organisation is already active.

If a signed-in user loses membership of the active organisation, the app clears
the selection and shows the picker, even if only one organisation remains.

The selection page (`/select-organization`) opens from **Switch organisation**
in the user menu and supports:

- Choosing from available organisations
- Filtering the organisations by name and loading more of them a page at a time
- Accepting pending invitations to gain access
- A **Manage instance** link to `/instance`, shown to instance administrators

## Invitations

Invitations are used to add users into organisations, and they are the only way
an account comes into being: registration is invitation only, enforced by the
sign-up endpoint. The first account of an instance comes from the init flow
instead.

Invitations always go to the active organisation. Administrators and managers
see all of its invitations, whoever sent them, and can change or delete any of
them, except that only administrators send, change or delete an invitation for
the administrator role. Your own invitations, across every organisation, appear on the account
and selection pages.

Current flows in app:

- **Invite user** on Users opens `/app/users/add`. One form invites a batch:
  it sets the **Role**, the **Expires** date (seven days ahead by default) and
  the **Email language** for everyone in it. Add addresses one at a time with
  **Add email field** or paste a list with **Bulk add emails**, then choose
  **Create invitations**.
- **View invitations** opens `/app/users/invites`, a table with the columns
  Email, Invitation ID, Expires, Status and Role. Each row offers **Copy
  invitation link** and **Delete organisation invitation**; selected rows can
  be removed with **Delete selected**, and **Download** exports the table.
- Register via invitation-aware sign-up flow
- See and respond to organisation invitations from account and selection pages

The sign-up endpoint validates the invitation ID, pending status, expiry, and
matching email address. The register page names the inviting organisation.
Signing up accepts only the linked invitation; other invitations remain pending
for explicit acceptance. One active organisation opens directly when there are
no pending invitations. Email verification remains optional for access.

## Groups

Groups are used for access assignment and resource sharing. Groups
(`/app/groups`) lists them with search and a Type column that tells Custom
groups from System groups; **Manage group** opens a group at
`/app/groups/<group id>`.

Every organisation has one system group, **All Members**. Every member of the
organisation belongs to it implicitly, so its member list cannot be edited, and
it cannot be renamed or deleted. Granting a resource to All Members shares it
with the whole organisation.

Current behaviour:

- Create custom groups
- Edit custom group name and description
- Delete custom groups
- Add/remove explicit members
- View implicit vs explicit membership labels

Creating, renaming, deleting a group and changing its membership need
`manage_groups`, so the Groups pages stay with admins and managers. Reading a
group does not: members and viewers see the groups they belong to, plus the
"All Members" group of their organisation. A group they are not in answers as
if it were not there.

The member picker offers only organisation members who are not yet in the
group, and several of them can be added at once.

System groups are immutable in the group detail view.

Members and viewers can discover colleagues by name and avatar in All Members
and select sharing recipients by user ID. Email fields and email search require
permission to manage groups.

## Resource Sharing

**Access & groups** opens the access dialog on a bot's page
(`/app/hub/bots/<bot id>`), a block's page (`/app/hub/blocks/<block id>`) and
an asset's page (`/app/hub/assets/<asset id>`). The bot editor's "Sharing and
access" step embeds the same controls. New people and groups are added from the
**People** and **Groups** tabs, each granted one of three resource roles:

- **Viewer** can find, use and read the resource.
- **Editor** can also edit it.
- **Manager** can also delete it and manage its access.

The person who created a resource owns it and holds all of these. Switching
**Visibility** between Private and Public asks for confirmation either way.

Access dialogs allow:

- Visibility management
- Group grants
- Direct grants
- A summary of the access inherited from the bots and blocks above

Listing or managing a resource's access, in its access dialog or through the
API, needs `manage_access` on that resource: you own it or hold a `manager`
grant on it. Organisation admins have no override. An admin who neither owns
nor manages a resource cannot list its grants, change its visibility, or share
it, and its access dialog is not offered to them.

Whoever holds `manage_access` on a resource shares it. Among them, organisation
admins and managers may grant to every group of the organisation; members and
viewers may grant to the groups they belong to and to "All Members", which
only ever receives a viewer grant. Other groups are neither offered in the access dialog nor accepted by
the API. The picker leaves out anyone who already holds a direct grant.
Several people and groups can be selected and granted the same role together.
If any of them cannot be granted, none of them are, and the error names each
one that failed.

A resource that has managers keeps at least one: a grant or revoke that would
take away its last manager is refused. A person or group that leaves still
loses its grants, even the last manager's, when they are removed from the
organisation, their account is deleted or the group is deleted. The owner keeps
managing the resource.

A private resource is reachable only by those it was granted to. Grants go
only to members and groups of the resource's organisation, but access follows
the person: someone who belongs to two organisations uses and links what they
can read in either. Sharing and linking across organisations are intended. A
public resource is the opposite: every signed-in user of the instance can find
and use it, whatever organisation they are in. Only the configuration and its
blocks are shared, because a public resource runs with the providers, models,
and quotas of the organisation it is used in.

The same access manager pattern is reused for:

- Assets
- Blocks
- Bots

### Inherited Access

Access cascades downwards as read-only. Sharing a bot lets its audience read
the blocks it links and the content items those blocks carry. So a resource can
be widely readable while its own grant list is empty, and the access dialog
says so: it reports the bots and blocks whose grants reach the resource, how
many groups and people arrive that way, and whether one of them is public.

Edit does not cascade: an editor or manager of a bot does not become an editor
of its blocks, and editing a block or a content item needs a grant on it. When
you give someone edit or manage on a bot, the access manager offers to give
them edit on the bot's blocks too, for the blocks you can share. Because
linking passes read on, linking requires read on what is linked: a bot links
only blocks its editor can read, and a repository attaches only content items
its editor can read.

Inherited access is shown, not edited. `manage_access` does not cascade, so a
grant that arrives from a bot is changed on that bot, which is where the
summary's links lead. Bots and blocks the viewer cannot read are counted rather
than named. Inherited access lasts only as long as the link above it: a direct
grant is what survives a block being detached from its bot.

Deleting a bot, block or content item removes its grants, its visibility and
the access it passed on through its links.

## Capability-Gated Workspace Sections

The sidebar's "Your workspace" group holds the OrcAI Assistant
(`/app/assistant`), the Library (`/app/hub`) and Administration. The Library
always shows; its Bots, Behaviour, Repositories and Assets items need `read`.
Administration shows when at least one of its items is allowed:

- Users (`/app/users`): `manage_members`
- Groups (`/app/groups`): `manage_groups`
- Quotas (`/app/quotas`): `manage_quotas`
- Analytics (`/app/analytics`): `view_analytics`
- Providers (`/app/providers`): `manage_providers`
- Models (`/app/models`): `manage_models`
- Organisation (`/app/organization`): `manage_organization`

Opening one of these paths without the permission leads away from it. See
[Workspace Administration](/docs/using-orcai/administration) for the pages.

## Practical Guidance

- Use groups for scalable access management.
- Use direct grants for exceptional one-off access.
- Keep high-impact capabilities (provider/model/quota management) limited to admins.

## Why Can Someone Not See A Bot Or Asset?

Work through these in order:

1. Check that the person is a member of the resource's organisation. Grants
   go only to members and groups of that organisation, and the access dialog
   offers no one else.
2. Open **Access & groups** on the resource. A private resource is visible to
   its owner, to the people granted it directly, to the members of the groups
   granted it, and to those who inherit access. With none of these, only its
   owner sees it.
3. Check group membership. A grant to a group reaches only its members; All
   Members reaches everyone in the organisation.
4. For a bot, check that it is published. Drafts appear only under "Your
   drafts" for those who can edit them, and chat setup offers published bots
   only.
5. An administrator or manager can open the person's page under Users
   (`/app/users/<user id>/edit`). Its **Effective resource access** card lists
   every bot, block and asset the person reaches and where the access comes
   from: a direct grant, a group, All Members, an inherited bot or block, or
   public visibility.
