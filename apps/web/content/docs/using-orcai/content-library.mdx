Assets (Library > Assets, `/app/hub/assets`) are the reusable source material OrcAI uses for retrieval, grounding, and citations.

## What You Can Do

- Add assets
- Move a chat upload into the library
- View an asset's details
- Edit metadata
- Reprocess an asset
- Manage access and groups
- Download the original file (if permitted)
- Delete an asset (if permitted)

## End-To-End Flow

1. Upload files on **Add assets** (`/app/hub/assets/add`). Each file becomes an asset as soon as its upload finishes, and OrcAI keeps the original in S3-compatible object storage.
2. Add metadata to the new assets, right away or later.
3. A background job processes the file and extracts its text, or describes its images.
4. Add the asset to one or more repositories, from the repository editor or the bot editor's Repositories step.
5. For each repository the asset belongs to, a background job vectorises it into that repository's index. This runs when processing finishes and when the asset is added to a repository.
6. Repositories are used in bots or attached directly to chats.

## Adding Assets

**Add assets** on the Assets page opens `/app/hub/assets/add`. It needs the `create_asset` permission.

Intake is file upload only:

1. **Upload assets**: select files and **Upload files**. Each file becomes an asset as soon as its upload finishes; there is nothing else to save.
2. **Uploaded assets**: the new assets are listed. **Metadata** opens a file's **Source details**, and **Save** stores them at once. Files that could not be added are listed with the reason. **Upload more** returns to the upload step, and **Done** goes to the Assets page.

Leaving the page while files are still uploading asks first; leaving anyway stops the upload, and those files are not added. Once a file's asset exists, leaving loses nothing.

The same flow runs inside an [OrcAI Assistant](/docs/using-orcai/assistant#uploads) conversation when the assistant asks for files, and in the repository editor's **Upload new assets** dialog, which also adds the new assets to the repository.

Accepted file types:

- Images: JPEG, PNG, GIF, WebP
- PDF
- Text: TXT, CSV, Markdown
- Office: DOC, DOCX, XLS, XLSX, PPT, PPTX

Limits: up to 64 MB per file and 100 files per upload.

## Library And Chat Uploads

The Assets page has two tabs. **Library** (the default) lists the assets uploaded on **Add assets**, in the repository editor or through the assistant. **Chat uploads** lists the files uploaded with a chat message; they are assets too, processed like any other, but kept out of the library so it stays tidy.

**Add to library** in a chat upload's card menu moves it to the **Library** tab. It needs edit access to the asset. Attaching a chat upload to a repository does not move it. Deleting a chat keeps its uploads; delete them from **Chat uploads**.

The asset pickers in the repository editor and the chat composer search both, and mark chat uploads with a **Chat upload** badge.

## Metadata

The metadata travels with the asset wherever it is reused. Fields:

- **Source title**
- **Source type**: Book, Journal Article, Web Source or Legal Text. Each type adds its own fields:
	- Book: **Author(s)**, **Citation label**, **Chapter title**, **Page range**
	- Journal Article: **Author(s)**, **Citation label**, **Journal name**, **Volume**, **Issue**, **Page range**, **DOI**
	- Web Source: **Author(s)**, **Citation label**, **Website name**, **External URL**, **Access date**
	- Legal Text: **Citation label**, **Legal reference**, **Jurisdiction**
- **External URL** (for types other than Web Source)
- **Relevance**: High, Medium or Low
- **Allow citations in answers**: whether the AI may make in-text references to this source. The asset page shows the setting as a badge. Answers do not yet respect it: an asset in a repository can be cited either way.

Edit metadata later with **Edit content** on the asset page, which opens `/app/hub/assets/<asset id>/edit`.

## The Asset Page

The asset page (`/app/hub/assets/<asset id>`) shows a preview of the file, its **Metadata**, and its **Preparation status**.

Actions, depending on your access to the asset:

- **Download**: download the original file.
- **Edit content**: edit the metadata.
- **Access & groups**: share the asset with people and groups. See [Access control](/docs/using-orcai/access-control).
- **More actions** menu:
	- **Reprocess**: run processing again.
	- **Delete asset**

## Processing Status And Reprocessing

Outside a repository, asset cards, the recent changes on Home and the **Preparation status** card on the asset page show how far processing of the file is:

| Status | Meaning |
| --- | --- |
| Queued | Waiting to be read. |
| Processing | The file is being read. |
| Ready | The file has been read and can be indexed by its repositories. |
| Failed | Reading the file failed after its retries. |

Inside a repository, each asset also has an indexing step, so its card on the repository page shows one more state, **Indexing**, between Processing and Ready, and Ready means searchable in that repository. See [Repository Blocks](/docs/using-orcai/bots#repository-blocks).

A failing step is retried automatically, so an asset stays Processing until its last attempt has failed. A failed asset says why: OrcAI cannot read the file type, no text or images were found (for example a scanned PDF whose text cannot be recognised), the file could not be read, preparing it took too long, or another error. The first two fail at once, since retrying cannot help.

On the **Preparation status** card, **Retry** appears for a failed asset you can edit, unless retrying cannot help, and queues processing again.

**Reprocess** is available from the card menu on the Assets page and from the asset page, when the asset is not Queued or Processing and you can edit it. It asks for confirmation, then reruns processing; the asset's repositories index it again afterwards. Reprocess is useful after parser or configuration changes.

Each repository keeps the indexing state of each of its assets. Editing a repository indexes only the assets it adds; the assets it keeps stay as they are. There is no job history in the app; operators find failed jobs in the worker logs and the pg-boss tables.

## Permissions And Access

Asset actions depend on your access to the asset:

- download
- edit
- delete
- manage_access

**Access & groups** opens the shared access dialog with People and Groups tabs.

## Relationship To Retrieval

Bots and chats do not retrieve from assets directly. Assets are added to repositories (database blocks), which are then attached to bots or chats. See [Bots and behaviour](/docs/using-orcai/bots).

In a chat, you can also attach an asset to a single message with **Add file** > **From assets**. The model receives the file, or its extracted text, with that message. See [Chat](/docs/using-orcai/chat#attachments-in-chat).

## Platform Dependencies

At system level, content workflows rely on:

- S3-compatible storage
- Worker processing pipeline
- Embedding generation
- Qdrant indexing

The embedding model and vector dimensions must stay compatible with existing collections.

<Callout title="Embedding compatibility" type="warn">
	Changing `EMBEDDING_MODEL` or `EMBEDDING_DIMENSIONS` after assets have already been indexed is not supported right now. Recreate the Qdrant collection and reprocess assets instead.
</Callout>
