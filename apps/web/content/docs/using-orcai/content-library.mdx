Assets (Library > Assets, `/app/library/assets`) are the reusable source material OrcAI uses for retrieval, grounding, and citations.

The Library, its pickers and the assistant's find tools show the bots, blocks
and assets of your active organisation that you can read: those made there and
those it added from the [catalogue](/docs/using-orcai/catalogue). A bot's
blocks and a repository's documents open through the bot or repository, so what
a shared bot contains is readable without appearing in your Library. Chat
pickers and the bots on the home page offer only the bots shared with you in
your active organisation.

## Browsing The Library

The Library (`/app/library`) shows everything your organisation can use. Its header has a search field and a **New** menu; a rail on the left (above the results on small screens) has:

- **All | Mine**: Mine keeps to what you can edit, as owner, manager or editor, directly or through a group. It stays on when you switch views, and the counts follow it.
- The views: **Overview** and one per kind (Bots, Behaviours, Repositories, Assets), each with its count.
- The view's filters, on a kind view or while searching. On narrow screens they open from **Filters**, which shows how many are set.

| View | Filters |
|---|---|
| Bots | **Status** (All, Published, Drafts), **Source**, **Only favourites** |
| Behaviours, Repositories | **Status** (All, Published, Drafts), **Source** |
| Assets | **Uploaded to** (Library, Chats), **Processing** (Any, Queued or running, Failed), **Suggestions to review** |
| Overview, while searching | **Status**, **Source** |

**Show in Library** on an upload's [Activity](/docs/using-orcai#activity) entry opens the Assets view with only the assets of that upload, wherever they are now. A bar above the results names the entry, and its × or any filter returns to the whole view.

**Source** tells apart what your organisation made (**Made in this
organisation**) from what it added from the catalogue (**Added from the
catalogue**). Assets are never added on their own, so searching for added items
leaves them out.

The **Overview** shows shelves: with Mine, your **Drafts** first, then your **Favourites**, then each kind with **See all**, which opens that kind's view. With fewer than six items it shows them all in one grid.

Search matches names and titles. On the Overview it searches every kind at once, in one list and one pager; on a kind view only that kind. Results are sorted **Newest** or **A to Z** and paged under the grid. Search, filters, sort, page and Mine are part of the address, so Back from a page returns to the same results and scroll position. Changing the search, a filter, the sort or Mine starts over on the first page.

**New** offers **Bot**, **Behaviour**, **Repository** and **Upload files**, each for roles with the matching `create_bot`, `create_block` or `create_asset` permission. An empty Library says whether you can create something or wait for others to share, and offers **Browse the catalogue**.

Every tile opens its page. Under its name it shows its owner, or "From" and the home organisation for what your organisation added from the catalogue. Its corner holds the star for published bots and a **…** menu with the actions your role allows. Something added from the catalogue is edited only in its home organisation: here admins and managers share it for use and remove it with **Remove from …**, and the setup editors of an added bot set its model on its page.

## What You Can Do

- Add assets
- Move a chat upload into the library
- View an asset's details
- Edit metadata
- Generate metadata with AI
- Reprocess an asset
- Manage access and groups
- Download the original file (if permitted)
- Delete an asset (if permitted)

## End-To-End Flow

1. Upload files on **Add assets** (`/app/library/assets/add`). Each file becomes an asset as soon as its upload finishes, and OrcAI keeps the original in S3-compatible object storage.
2. Add metadata to the new assets, right away or later. With a utility model, OrcAI generates it for library uploads once the file is processed; see [Metadata generated with AI](#metadata-generated-with-ai).
3. A background job processes the file and extracts its text. The organisation's [utility model](/docs/using-orcai/administration#utility-model) describes each image, an image file or a figure in a document, so its content can be found by search. The descriptions are saved with the extracted text, and indexing in every repository reuses them. When the quota runs out partway through a document, the descriptions written so far are charged but not saved, so a retry describes those images again.
4. Add the asset to one or more repositories, from the repository editor or the bot editor's Repositories step.
5. For each repository the asset belongs to, a background job vectorises it into that repository's index. This runs when processing finishes and when the asset is added to a repository.
6. Repositories are used in bots or attached directly to chats.

## Adding Assets

**New** > **Upload files** in the Library opens `/app/library/assets/add`. It needs the `create_asset` permission.

Intake is file upload only:

1. **Upload assets**: select files and **Upload files**. Each file becomes an asset as soon as its upload finishes; there is nothing else to save.
2. **Uploaded assets**: the new assets are listed. With a utility model, each shows **Generating metadata** until its generated title and description appear; you can leave, and the results land in the library. The upload and its preparation also show in [Activity](/docs/using-orcai#activity). **Metadata** opens a file's **Source details**, and **Save** stores them at once. Files that could not be added are listed with the reason. **Upload more** returns to the upload step, and **Done** goes to the Assets view.

Leaving the page while files are still uploading asks first; leaving anyway stops the upload, and those files are not added. Once a file's asset exists, leaving loses nothing.

The same flow runs inside an [OrcAI Assistant](/docs/using-orcai/assistant#uploads) conversation when the assistant asks for files, and in the repository editor's **Upload new assets** dialog, which also adds the new assets to the repository.

Accepted file types:

- Images: JPEG, PNG, GIF, WebP
- PDF
- Text: TXT, CSV, Markdown
- Office: DOC, DOCX, XLS, XLSX, PPT, PPTX

Limits: up to 64 MB per file and 100 files per upload.

## Library And Chat Uploads

The Assets view's **Uploaded to** filter has two choices. **Library** (the default) lists the assets uploaded on **Add assets**, in the repository editor or through the assistant. **Chats** lists the files uploaded with a chat message; they are assets too, processed like any other, but kept out of the library so it stays tidy. The Library's counts and its Overview leave chat uploads out.

**Add to library** in a chat upload's tile menu moves it to the library and generates its metadata like a library upload. It needs edit access to the asset. Attaching a chat upload to a repository does not move it. Deleting a chat keeps its uploads; delete them from **Uploaded to** > **Chats**.

The asset pickers in the repository editor and the chat composer search both, and mark chat uploads with a **Chat upload** badge.

## Metadata

The metadata travels with the asset wherever it is reused. Fields:

- **Source title**
- **Description**: two or three sentences on what the source is about, up to 300 characters. Cards show it, and the model reads it in the list of a repository's documents to pick what to search.
- **Language**: the source's language as a code such as `en` or `de-CH`.
- **Source type**: Book, Journal Article, Web Source or Legal Text. Each type adds its own fields:
	- Book: **Author(s)**, **Citation label**, **Chapter title**, **Page range**
	- Journal Article: **Author(s)**, **Citation label**, **Journal name**, **Volume**, **Issue**, **Page range**, **DOI**
	- Web Source: **Author(s)**, **Citation label**, **Website name**, **External URL**, **Access date**
	- Legal Text: **Citation label**, **Legal reference**, **Jurisdiction**
- **External URL** (for types other than Web Source)

Edit metadata later with **Edit content** on the asset page, which opens `/app/library/assets/<asset id>/edit`. Saving stores only the fields you changed, so metadata generated while the editor was open is kept. Changing the source type removes, on save, the fields the new type does not have.

## Metadata Generated With AI

When the organisation has a [utility model](/docs/using-orcai/administration#utility-model), it writes an asset's metadata from the start of its extracted text and the details the parser found (title, authors, keywords, page count, language): the title, the source type and its fields, a citation label in APA 7 style, a description and the language. Generated text is in the document's language. For an image file, the description written while processing the image supplies the title, description and language. Each run draws on the utility model's quota pools.

- **After upload**: once a library upload is processed, its metadata is generated in the background. A chat upload gets it when it is added to the library. Only empty fields are filled, and the title only while it is still the uploaded file name; values you save in the meantime always win. Fields that do not fit the source type you chose are kept for review instead.
- **Generate with AI** in the metadata editor generates a suggestion for an asset you can edit, also for assets uploaded before or edited since. The editor shows **Generating...**; you can leave, and the asset page then says **Suggestions ready** with **Review**. **Suggested metadata** lists each field with its current and suggested value; empty fields are selected. **Use selected** puts the chosen values into the form, which saves them with **Save**; **Dismiss** drops the suggestion. The **Suggestions to review** filter on the Assets view lists every asset you can edit that has a suggestion waiting.
- **Generate missing metadata** above the Assets view's library uploads generates metadata, filling empty fields, for every processed library asset of the organisation you can edit whose metadata was never generated or failed. It asks first and shows how many assets that is.
- The [OrcAI Assistant](/docs/using-orcai/assistant) can do the same for assets you name, after you confirm. It never overwrites values; to replace them, use **Generate with AI** or tell it the values.

While metadata is generated, cards, the upload list and the asset page show **Generating metadata**. A failed run says why on the asset page; when the quota ran out, run it again once the pool resets. Without a utility model, nothing is generated, **Generate with AI** is disabled with a hint (admins get a link to the organisation settings), and **Generate missing metadata** is hidden. Generating metadata never affects whether an asset is ready for its repositories.

## The Asset Page

The asset page (`/app/library/assets/<asset id>`) shows a preview of the file, its **Metadata**, and its **Preparation status**.

Actions, depending on your access to the asset:

- **Download**: download the original file.
- **Edit content**: edit the metadata.
- **Access & groups**: share the asset with people and groups. See [Access control](/docs/using-orcai/access-control).
- **More actions** menu:
	- **Reprocess**: run processing again.
	- **Delete asset**

## Processing Status And Reprocessing

Outside a repository, asset cards, the recent changes on Home and the **Preparation status** card on the asset page show how far processing of the file is:

| Status | Meaning |
| --- | --- |
| Queued | Waiting to be read. |
| Processing | The file is being read. |
| Ready | The file has been read and can be indexed by its repositories. |
| Failed | Reading the file failed after its retries. |

Inside a repository, each asset also has an indexing step, so its card on the repository page shows one more state, **Indexing**, between Processing and Ready, and Ready means searchable in that repository. See [Repository Blocks](/docs/using-orcai/bots#repository-blocks).

A failing step is retried automatically, so an asset stays Processing until its last attempt has failed. A failed asset says why: OrcAI cannot read the file type, or the utility model cannot read images for an image file; no text or images were found (for example a scanned PDF whose text cannot be recognised); the file could not be read; preparing it took too long; the quota ran out while describing images; or another error. The first two fail at once, since retrying cannot help. A used-up quota also fails at once, with nothing half prepared; retry once the pool resets. Without a utility model that reads images, figures in documents are skipped and the rest of the document is prepared.

On the **Preparation status** card, **Retry** appears for a failed asset you can edit, unless retrying cannot help, and queues processing again.

**Reprocess** is available from the tile menu in the Assets view and from the asset page, when the asset is not Queued or Processing and you can edit it. It asks for confirmation, then reruns processing; the asset's repositories index it again afterwards. Reprocess is useful after parser or configuration changes.

Each repository keeps the indexing state of each of its assets. Editing a repository indexes only the assets it adds; the assets it keeps stay as they are. [Activity](/docs/using-orcai#activity) shows the uploads and retries you started and the failures that need you. Operators find failed jobs in the worker logs and the pg-boss tables.

## Permissions And Access

Asset actions depend on your access to the asset:

- download
- edit
- delete
- manage_access

**Access & groups** opens the shared access dialog with People and Groups tabs.

## Relationship To Retrieval

Bots and chats do not retrieve from assets directly. Assets are added to repositories (database blocks), which are then attached to bots or chats. See [Bots and behaviour](/docs/using-orcai/bots).

In a chat, you can also attach an asset to a single message with the paperclip (**Attach files**) > **From assets**. The model receives the file, or its extracted text, with that message. See [Chat](/docs/using-orcai/chat#attachments-in-chat).

## Platform Dependencies

At system level, content workflows rely on:

- S3-compatible storage
- Worker processing pipeline
- Embedding generation
- Qdrant indexing

The embedding model and vector dimensions must stay compatible with existing collections.

<Callout title="Embedding compatibility" type="warn">
	Changing `EMBEDDING_MODEL` or `EMBEDDING_DIMENSIONS` after assets have already been indexed is not supported right now. Recreate the Qdrant collection and reprocess assets instead.
</Callout>
