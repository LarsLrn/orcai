## Creating Accounts

Creating an account is invitation only, enforced by the sign-up endpoint itself: it
requires the ID of a pending, unexpired invitation matching the address. There is no
open account creation to disable, and no setting turns one on.

- The first account of an instance comes from the init flow at `/init`,
  which writes the user directly and is therefore not affected by the rule.
- Every later account is created from an invitation link an organisation
  admin sends. Creating the account accepts that invitation and writes its
  membership. Other invitations remain pending for explicit acceptance.
  Membership, invitation status, and permission intent commit atomically;
  permission delivery retries from the outbox after commit.
- Existing accounts are unaffected. Sign-in, password reset, and invitations to
  further organisations keep working as before.

## Permission delivery

Every change to memberships, groups, grants, bots, blocks, and assets commits its
SpiceDB relationship changes to the `authz_outbox` table in the same
transaction. The app delivers them to SpiceDB in commit order, one deliverer
at a time, right after the request and every 10 seconds in the background.

A failed delivery retries with backoff up to 8 minutes apart until it
succeeds, whatever the cause: SpiceDB unreachable, timing out, refusing the
app's credentials, or rejecting the change, for example because a deploy runs
the new code before the new SpiceDB schema is applied. Meanwhile the failing
event holds back every newer one, so permissions stay consistent with the
database but stop updating until the cause is fixed.

Each failed attempt logs an `authz.delivery_blocked` line with the event's
`eventId`, `seq`, `attempts`, `ageSeconds`, the gRPC status as `code`, and the
`cause`. It is a warning at first and an error once the event is older than
5 minutes. A blocked queue therefore shows as a series of these lines for the
same `eventId`. To see it in the database:

```sql
SELECT id, seq, attempts, created_at, next_attempt_at
FROM authz_outbox
WHERE status IN ('pending', 'failed')
ORDER BY seq
LIMIT 10;
```

Fix the cause the log line names, for example by applying the SpiceDB schema.
The next attempt then delivers the event and every one behind it.

An event can also be skipped by hand when it can never succeed:

```sql
UPDATE authz_outbox SET status = 'dead_letter' WHERE id = '<eventId>';
```

Delivery then moves on to the next event. SpiceDB is missing the skipped
change, so correct the affected relationships, for example by repeating the
change in the app. An event whose payload the app cannot read is moved to
`dead_letter` automatically and logged as `authz.dead_letter` at error level.

## Migrations

Apply application database migrations with:

```bash title="Repository root"
bun run --filter @orcai/db migrate
```

Generate a new Drizzle migration during development with:

```bash title="Repository root"
bun run --filter @orcai/db generate
```

Apply the SpiceDB schema with:

```bash title="Repository root"
bun run --filter @orcai/spice-db up
```

Inspect SpiceDB schema migration status with:

```bash title="Repository root"
bun run --filter @orcai/spice-db status
```

## Health

`GET /api/health` answers `200` when PostgreSQL and SpiceDB answer within three seconds, and `503` otherwise. It needs no session and returns no body, so it is safe to expose to a load balancer or orchestrator. The Compose `app` healthcheck uses it.

Instance admins see the full picture on the Health page (`/instance/health`): every dependency, the background processes, queue counts, email delivery, versions and the app's configuration with secrets hidden. See [Instance management](/docs/using-orcai/administration#instance-management).

## Email delivery

The workers send email from the `notification_outbox` table. Each sent row records its `delivery_channel`: `smtp`, or `log` when the workers have no SMTP configuration and only wrote the message to their log. A `log` row is still marked `sent`, so check the channel, or the Health page, which warns when the latest email only reached the log. The app process has no SMTP settings of its own.

## Workers

Keep workers running alongside the app. If workers are stopped, uploads and scheduled maintenance jobs may remain queued.

Every process that runs pg-boss registers in its instance registry under a name: the app as `app`, the workers as `workers`, each with its host and process id. The Health page lists them and fails its workers check when no `workers` process is live.

Processing (`process-asset-job`) and indexing (`vectorize-asset-job`) jobs run up to four times, a minute apart, and an attempt times out after an hour. A job whose attempts are used up moves to its dead letter queue (`process-asset-dead-letter-job`, `vectorize-asset-dead-letter-job`), whose worker marks the asset, or the asset in that repository, as failed. The workers create the queues and their dead letter settings at startup. The failed job, with its last error, stays in the pg-boss tables until retention removes it; the worker logs carry the same error.

Data exports (`data-export-job`) are the exception: the app server works them, one at a time per app instance, because their chat transcripts need the app's code. The workers still create the queue and its dead letter queue (`data-export-dead-letter-job`), and the app starts working it once both exist, so a deployment without workers cannot export data. The retry and timeout settings are the same; an export whose attempts are used up is marked failed and the user can start a new one. Stopping the app interrupts a running export, and pg-boss retries it.

The `activity-cleanup-job` runs every hour and keeps each user's activity bounded. It deletes an entry seven days after its work finished, or once the user dismissed it, and never deletes an entry whose work is still running. Failures and suggestions that need a user's attention are read from the assets and exports themselves, so the cleanup never removes one.

## Upload Storage Lifecycle

Uploads land under `staging/` in the `uploads` bucket. Creating the asset moves the file to its final key, so `staging/` only holds files no asset was created from, such as an upload abandoned mid-flight.

Each time the workers start, they put the lifecycle rule `expire-staged-uploads` on the `uploads` bucket: objects under `staging/` expire one day after upload, and incomplete multipart uploads are aborted one day after they started. Other lifecycle rules on the bucket stay as they are. The rule never matches an asset's file. If the storage provider rejects it, the workers log the error and keep running.

The storage provider enforces the rule, not OrcAI. SeaweedFS runs lifecycle in its plugin worker, once a day, so a staged file can stay up to about two days. A storage provider without bucket lifecycle support keeps staged leftovers until you remove them.

## Data Export Archives

Data export archives land under `exports/` in the same bucket and can be downloaded for 24 hours. The workers delete them themselves, so the removal does not depend on the storage provider: the `data-export-expire-job` runs every ten minutes and deletes every object under `exports/` that is older than 25 hours, the 24 hour download window plus the hour an export may take to build, including archives whose export or user no longer exists. The app refuses to download an export after 24 hours before the job has run.

## Asset Preparation

If OCR or extraction fails, verify:

- Worker process is running.
- Tesseract is installed when running workers on the host.
- `KREUZBERG_OCR_LANGUAGE` only references installed language packs.
- Images are described by the organisation's utility model, which needs the image capability; without it, image files fail and figures inside files are skipped.
- Object storage credentials and bucket setup are valid.

## Retrieval

If retrieval quality or indexing fails, verify:

- `OPENAI_COMPATIBLE_BASE_URL` and `OPENAI_COMPATIBLE_API_KEY`.
- `EMBEDDING_MODEL`.
- `EMBEDDING_DIMENSIONS`.
- Qdrant availability and API key.

Do not change embedding model or dimensions on a live indexed dataset without recreating the collection and reindexing.

## SpiceDB Connectivity

If SpiceDB connections fail, verify:

- `SPICEDB_ENDPOINT`.
- `SPICEDB_TOKEN`.
- `SPICEDB_SECURITY` matches your deployment mode.
