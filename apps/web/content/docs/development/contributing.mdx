You contribute code and documentation to the main OrcAI repository through a branch, local checks and a pull request.

## Before you start

- Use Bun `>=1.3.10`.
- Start the per-worktree stack as described under [Recommended workflow](/docs/development#recommended-workflow).
- Create a branch from the latest main branch.

## Typical contribution flow

1. Update `main` and create a feature or fix branch.
2. Implement your changes.
3. Run the relevant checks locally.
4. Commit using Conventional Commit format.
5. Open a pull request with clear scope and validation notes.

## Branch naming

Use short, descriptive branch names, for example:

- `feat/chat-branch-switcher-fixes`
- `fix/repository-playground-empty-state`
- `docs/self-hosting-config-update`

## Commit message format

commitlint (`@commitlint/config-conventional`) checks every commit message.

Use Conventional Commits, for example:

- `feat(chat): add branch filter to chat list`
- `fix(workers): handle missing qdrant payload field`
- `docs(self-hosting): clarify spicedb security modes`

## Local validation

While iterating, run Biome, the TypeScript check, the migration check, Knip and the unit tests. None of them needs the stack.

```bash title="Repository root"
bun run verify
```

Before you open a pull request, run what the `validate` job in CI runs. It adds ESLint, the docs type check and the production build.

```bash title="Repository root"
bun run ci
```

If your change touches user-facing flows, run the end-to-end suite as well. It needs the stack running and resets the stack's data, see [End-to-end tests](/docs/development/testing).

```bash title="Repository root"
bun run stack e2e
```

## Git hooks and CI

- `pre-commit` runs `lint-staged`, which applies Biome's safe fixes and formatting to the staged files and fails on remaining errors. Biome lints Markdown but does not format it, because it pads table columns.
- `commit-msg` runs commitlint.
- `pre-push` runs `bun run prepush`, which is `bun run lint-full`.

GitHub Actions runs `bun run ci` and the end-to-end suite as two blocking checks, `validate` and `e2e`, for pushes to `main` and for pull requests. Pull requests that only touch docs content or Markdown skip the end-to-end suite. Pull request runs check the branch merged into `main`, so rebase onto `main` when CI fails on something a local run passes.

## Pull request expectations

Include the following in your PR description:

- What changed and why.
- Risk level and impacted areas (`apps/app`, `apps/workers`, `apps/web`, `packages/*`).
- Validation performed (commands run and outcomes).
- Screenshots for user-facing UI changes.
- Any TODOs or follow-up work.

## Documentation contributions

If your change modifies user flow, operations, or configuration behaviour, update the relevant docs in `apps/web/content/docs` and `README.md` in the same change.

A docs page is an MDX file in a section folder under `apps/web/content/docs`. List it in that folder's `meta.json`, which sets the sidebar order, and give it a `title` and a `description` in its frontmatter. Check the page and its links with `bun run --filter @orcai/web build`.

The OrcAI Assistant answers from these pages. The docs site serves an index at `/llms.txt` with each page's title, URL and description, every page as Markdown at `/docs/<page>.md`, and all pages in one file at `/llms-full.txt`. The Assistant reads the index first and picks pages by their description, so the description names what the page covers. It fetches from `WEB_INTERNAL_URL`, or `WEB_URL` when that is unset, see [Configuration](/docs/self-hosting/configuration).

Any change to UI strings, emails or docs pages uses the terms in the [Glossary](/docs/development/glossary), in English and German, and follows the writing skill in `.agents/skills/writing/`. Coding agents load the skill on their own.

## Model-facing text

System prompts, tool and parameter descriptions, structured-output instructions and the text tools return to the model follow the prompting skill in `.agents/skills/prompting/`. Coding agents load it on their own.

Run the prompt evals before and after such a change and put the comparison in the pull request:

```bash title="Repository root"
bun run prompt-evals                                   # on the unchanged code
bun run prompt-evals --compare <results file>          # on the change
```

The evals call real models through OpenRouter with the key in `OPENROUTER_API_KEY` or `~/.config/orcai/openrouter.env`, and a full run costs about $0.30. `PROMPT_EVALS_ENDPOINT` points them at another OpenAI-compatible endpoint. `.agents/skills/prompting/EVALS.md` describes the flags, the cases and how to add one.

## Search and extraction changes

A change to extraction, chunking, figure descriptions, indexing or search ranking changes how often search finds the passage that answers a question. Run the retrieval evals before and after such a change and put the comparison in the pull request:

```bash title="Repository root"
bun run stack exec -- bun run retrieval-evals                            # on the unchanged code
bun run stack exec -- bun run retrieval-evals --compare <results file>   # on the change
```

The evals extract a fixed corpus with the extraction profile the workers use, describe its figures with a vision model, index the passages in a collection of their own in the stack's Qdrant and search them as the search tool does. About 70 questions in German and English each name the passage or figure that answers them. For every configuration the table reports how often that passage comes first (Hit@1), within the first three (Hit@3) or among all results (Hit@results), the mean reciprocal rank (MRR) and how often the first result answers and names the right page (Page@1). A line below the table lists questions whose answer no passage holds, which points to extraction rather than ranking.

The corpus holds public documents and generated ones. Public documents are German official texts, in the public domain or under CC BY. They are fetched on the first run, checked against the digest in `apps/app/scripts/retrieval-evals/corpus.ts` and kept in `~/.cache/orcai/retrieval-evals` or `RETRIEVAL_EVALS_CACHE`, never in the repository. Generated documents are built from text in the repository with the e2e suite's Chromium: a report with a logo on every page, a table longer than a chunk and a chart, a scanned notice and a slide deck. The OCR models the workers image installs are fetched to the same cache. Figure descriptions and vectors are cached as well, so a repeated run calls the models only for what changed.

The evals need the stack and an OpenAI-compatible endpoint that serves the embedding and vision models:

| Variable or flag | Meaning |
| --- | --- |
| `RETRIEVAL_EVALS_ENDPOINT`, `RETRIEVAL_EVALS_API_KEY` | The endpoint and its key. |
| `RETRIEVAL_EVALS_RPM` | The requests per minute, spread evenly, by default 60, which also stays under 10 in any 10 seconds. |
| `--embedding-model`, `--query-prefix`, `--passage-prefix` | The embedding model and its prefixes, by default `e5-mistral-7b-instruct` with the E5 query instruction. |
| `--vision-model` | The model that describes figures, by default `gemma-4-31b-it`. |
| `--ocr-language` | The Tesseract languages, by default `eng+deu` as in the workers image. |
| `--chunk-sizes` | Chunk sizes in characters, by default `1000,2000`, each with an overlap of a fifth. |
| `--limits` | Results per search, by default `6,12`. The search tool returns at most 8 passages, so a larger limit measures a higher cap. |
| `--modes` | Retrieval modes, by default `hybrid,dense,sparse`. |
| `--headers` | What the embedded text of a passage starts with: `heading` by default, its heading path as indexing adds it, `title` for the document title before the heading path, or `none`. |
| `--stopwords` | BM25 stopwords: `indexing` by default, the stopwords indexing uses, or `none`, or Qdrant's lists for languages joined by `+`, such as `german+english`. |
| `--questions` | Only the questions whose id starts with one of these, such as `de/` or `en/naca-scan`. |

Each value of a list runs on its own, so `--headers heading,title --stopwords indexing,none` compares four indexes. Results are saved in `apps/app/scripts/retrieval-evals/results`. Compare only runs on the same endpoint and models. A comparison with a run on another corpus or question set stops before it starts. Hybrid rankings can differ by a question or two between identical runs, as fusion breaks ties in any order, while dense and sparse rankings repeat exactly. To add a question, write it in your own words in `questions.ts` with the document, the page and short quotes the answering passage holds, such as a table row's label and its value.

## Generated and derived files

| File | Generated by | Committed |
| --- | --- | --- |
| `apps/app/src/routeTree.gen.ts`, `apps/web/src/routeTree.gen.ts` | The TanStack Router plugin, whenever the app's or the docs site's `dev` or `build` runs | Yes |
| `packages/db/migrations` | `bun run stack exec -- bun run --filter @orcai/db generate`, see [Commands](/docs/development/commands#database-and-authorisation) | Yes |
| `apps/app/src/paraglide`, `packages/notifications/src/paraglide` | `paraglide:compile`, see [Localisation](/docs/development/localisation) | No |
| `apps/web/.source` | `fumadocs-mdx`, which runs after `bun install`, in `types:check` and in the docs site's `dev` and `build` | No |

After adding, moving or deleting a route file, run the app or docs site once and commit the updated route tree.

## Security reports

Do not open a public issue for a suspected vulnerability. Follow the private reporting process in the repository's `SECURITY.md`.
