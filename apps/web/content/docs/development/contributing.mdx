title: Contributing to the main repo
description: How to contribute code and documentation to OrcAI, from branch to pull request.
---

You contribute code and documentation to the main OrcAI repository through a branch, local checks and a pull request.

## Before you start

- Use Bun `>=1.3.10`.
- Start the per-worktree stack as described under [Recommended workflow](/docs/development#recommended-workflow).
- Create a branch from the latest main branch.

## Typical contribution flow

1. Update `main` and create a feature or fix branch.
2. Implement your changes.
3. Run the relevant checks locally.
4. Commit using Conventional Commit format.
5. Open a pull request with clear scope and validation notes.

## Branch naming

Use short, descriptive branch names, for example:

- `feat/chat-branch-switcher-fixes`
- `fix/repository-playground-empty-state`
- `docs/self-hosting-config-update`

## Commit message format

commitlint (`@commitlint/config-conventional`) checks every commit message.

Use Conventional Commits, for example:

- `feat(chat): add branch filter to chat list`
- `fix(workers): handle missing qdrant payload field`
- `docs(self-hosting): clarify spicedb security modes`

## Local validation

While iterating, run Biome, the TypeScript check, the migration check and the unit tests. None of them needs the stack.

```bash title="Repository root"
bun run verify
```

Before you open a pull request, run what the `validate` job in CI runs. It adds ESLint, the docs type check and the production build.

```bash title="Repository root"
bun run ci
```

If your change touches user-facing flows, run the end-to-end suite as well. It needs the stack running and resets the stack's data, see [End-to-end tests](/docs/development/testing).

```bash title="Repository root"
bun run stack e2e
```

## Git hooks and CI

- `pre-commit` runs `lint-staged`, which applies Biome's safe fixes and formatting to the staged files and fails on remaining errors.
- `commit-msg` runs commitlint.
- `pre-push` runs `bun run prepush`, which is `bun run lint-full`.

GitHub Actions runs `bun run ci` and the end-to-end suite as two blocking checks, `validate` and `e2e`, for pushes to `main` and for pull requests. Pull requests that only touch docs content or Markdown skip the end-to-end suite. Pull request runs check the branch merged into `main`, so rebase onto `main` when CI fails on something a local run passes.

## Pull request expectations

Include the following in your PR description:

- What changed and why.
- Risk level and impacted areas (`apps/app`, `apps/workers`, `apps/web`, `packages/*`).
- Validation performed (commands run and outcomes).
- Screenshots for user-facing UI changes.
- Any TODOs or follow-up work.

## Documentation contributions

If your change modifies user flow, operations, or configuration behaviour, update the relevant docs in `apps/web/content/docs` and `README.md` in the same change.

A docs page is an MDX file in a section folder under `apps/web/content/docs`. List it in that folder's `meta.json`, which sets the sidebar order, and give it a `title` and a `description` in its frontmatter. Check the page and its links with `bun run --filter @orcai/web build`.

The OrcAI Assistant answers from these pages. The docs site serves an index at `/llms.txt` with each page's title, URL and description, every page as Markdown at `/docs/<page>.md`, and all pages in one file at `/llms-full.txt`. The Assistant reads the index first and picks pages by their description, so the description names what the page covers. It fetches from `WEB_INTERNAL_URL`, or `WEB_URL` when that is unset, see [Configuration](/docs/self-hosting/configuration).

Any change to UI strings, emails or docs pages uses the terms in the [Glossary](/docs/development/glossary), in English and German, and follows the writing skill in `.agents/skills/writing/`. Coding agents load the skill on their own.

## Model-facing text

System prompts, tool and parameter descriptions, structured-output instructions and the text tools return to the model follow the prompting skill in `.agents/skills/prompting/`. Coding agents load it on their own.

Run the prompt evals before and after such a change and put the comparison in the pull request:

```bash title="Repository root"
bun run prompt-evals                                   # on the unchanged code
bun run prompt-evals --compare <results file>          # on the change
```

The evals call real models through OpenRouter with the key in `OPENROUTER_API_KEY` or `~/.config/orcai/openrouter.env`, and a full run costs about $0.30. `.agents/skills/prompting/EVALS.md` describes the flags, the cases and how to add one.

## Generated and derived files

| File | Generated by | Committed |
| --- | --- | --- |
| `apps/app/src/routeTree.gen.ts`, `apps/web/src/routeTree.gen.ts` | The TanStack Router plugin, whenever the app's or the docs site's `dev` or `build` runs | Yes |
| `packages/db/migrations` | `bun run stack exec -- bun run --filter @orcai/db generate`, see [Commands](/docs/development/commands#database-and-authorisation) | Yes |
| `apps/app/src/paraglide`, `packages/notifications/src/paraglide` | `paraglide:compile`, see [Localisation](/docs/development/localisation) | No |
| `apps/web/.source` | `fumadocs-mdx`, which runs after `bun install`, in `types:check` and in the docs site's `dev` and `build` | No |

After adding, moving or deleting a route file, run the app or docs site once and commit the updated route tree.

## Security reports

Do not open a public issue for a suspected vulnerability. Follow the private reporting process in the repository's `SECURITY.md`.
