## Runtime Components

- React 19 and TanStack Start power the user interface and server runtime.
- TanStack Router, Query, and Form are used for client routing and data workflows.
- oRPC defines typed backend contracts.
- Better Auth handles authentication.
- Drizzle ORM manages PostgreSQL access and migrations.
- pg-boss coordinates background jobs.
- Qdrant stores vector indexes.
- SpiceDB handles authorisation relationships and permission checks.
- S3-compatible storage stores uploaded and processed files.
- Kreuzberg and Tesseract handle text extraction and OCR.
- The AI SDK talks to each provider's API through its kind (OpenAI-compatible, OpenAI or Anthropic); titles, embeddings and workers use the instance's OpenAI-compatible endpoint.

## Asset Preparation Flow

1. A user uploads files through the app. The browser puts each file under `staging/` in S3-compatible object storage with a URL the app signed.
2. Right after the upload, the browser calls `asset.createFromUploads`. The intake module (`apps/app/src/lib/assets/intake.ts`) checks each staged file against the signed upload, moves it to the asset's key, and creates the asset row with its owner. Bucket, keys and origin (library or chat) come from the signed-in user and the upload route, never from the client. Each file gets its own result, and repeating an upload returns the same asset.
3. The app creates background jobs.
4. Workers extract content from the uploaded files.
5. Workers create processed artifacts and metadata.
6. Workers generate embeddings using the configured model endpoint.
7. Workers write vector data to Qdrant.
8. Chat tools query Qdrant and retrieve relevant content for model calls.

## Profile Pictures And Logos

Profile pictures and organisation logos are not assets: they need no
preparation, no SpiceDB relationships and no presigned reads.

1. The browser crops the chosen image to a 256 by 256 pixel WebP and uploads it through the `profileImage` or `organizationLogo` route, which signs one WebP of at most 256 KB under `staging/` like any upload.
2. `user.setImage` or `organization.setLogo` (organisation admins) hands the upload to the image module (`apps/app/src/lib/images/images.ts`). It checks the upload belongs to the caller, checks the stored object's type and size, copies it to a fresh key under `images/` and swaps the column under a row lock. The replaced object and the staged copy are deleted afterwards, best effort; a failure leaves a small unreferenced object, and the `staging/` lifecycle rule expires abandoned uploads. No lifecycle rule matches `images/`.
3. `user.image` and `organization.logo` hold the image's app path, `/api/images/<users|organizations>/<id>/<uuid>.webp`, so a new image gets a new URL. Deleting an account or an organisation deletes its image the same way.
4. `GET /api/images/...` (`apps/app/src/routes/api/images/$.ts`) streams an image to any signed-in user, 401 without a session and 404 for a path no column references. It answers `Cache-Control: private, no-cache` with an ETag, so browsers revalidate with a cheap 304 and a removal or sign-out applies at once, and `X-Content-Type-Options: nosniff`.

The 256-pixel size and the dropped metadata are guaranteed for uploads through the app's crop dialog only. The server checks type and size but does not decode or re-encode images; a client calling the API directly can store any WebP-labelled bytes up to 256 KB, which the route serves only as `image/webp`.

## Authorisation Flow

The app stores domain records in PostgreSQL and uses SpiceDB for relationship-based authorisation. Permission middleware checks whether a user can access or mutate a resource before executing protected operations.

### Read Consistency

Authorisation reads are near real-time by default: SpiceDB answers them with `minimizeLatency`, which can miss a permission change made moments earlier. A request that writes authorisation returns the resulting zedToken in the response `meta` and sets a `zed_token` cookie for 60 seconds, so the browser's following reads are at least as fresh as that write.

The sign-up response carries the same cookie for the membership it grants, so a new account's first reads already see it.

API consumers outside the browser can send the token back in the `X-Zed-Token` header, and some procedures also accept it as a `zedToken` input to pin the freshness of a single call.

A response without `meta.zedToken` means the request wrote nothing to SpiceDB inline; the write is queued and applied shortly after, so a read issued immediately may still see the previous state.

## AI Flow

Chat generation uses configured providers and models. Retrieval tools can search repositories, list their assets, and fetch pages or passages before the model's response is generated.

The OrcAI Assistant's tools call OrcAI's procedures as the signed-in user through the per-namespace Effect clients, so every middleware and authorisation check runs as it does for the app. Core tools are always offered; the bots, sharing and people groups load on demand through `loadTools`, filtered by the user's organisation permissions. Tools that destroy, revoke, widen access, change a role or send something out need approval: the turn pauses, and once the user answers it resumes on the same message through `ai.continue`. The Assistant's plan is its newest `updatePlan` call; the first plan of a conversation needs the same approval, and create tools become callable only once a plan has been approved. How loading reaches the model depends on the provider's tool-loading strategy. With `references` (Anthropic models with tool search), every tool is declared up front, the group tools deferred. A loaded group and the create tools unlocked by the approved plan surface through `tool-reference` parts in the tool result, and create tools check for an approved plan when they run. With `active-tools` (other provider kinds and older Claude models), a loaded group's tools and the unlocked create tools join the request's tool list.

Asset preparation describes images, both image files and figures inside files, once with the organisation's utility model and stores the descriptions with the extraction; indexing reads them from there. The calls are metered against the organisation's quota pools and attributed to the uploader.

## Observability

Umami analytics is optional. OpenTelemetry export is on when `OTEL_EXPORTER_OTLP_ENDPOINT` is set; `@orcai/observability` then builds one resource for traces, logs and metrics from `OTEL_RESOURCE_ATTRIBUTES` and the service name and version, and registers the tracer and meter providers globally for libraries that use the OpenTelemetry API.

- Traces: the app opens one server span per request named `<method> <route template>` (RPC requests carry the procedure path, auth requests only the template); oRPC, Better Auth, Effect SQL, pg-boss `send`, AI SDK and HTTP client spans nest under it. A worker's `process <queue>` span continues the trace of the request that queued the job; batches of several jobs link to each producer instead. Effects started from promise-based code join the active span through `withActiveSpan` in `@orcai/observability` and `runPromise` in `apps/app/src/lib/effect/runtime.ts`; oRPC's Effect handlers and middlewares join theirs through `effect/wrap`. A client error such as a 403 does not fail the span, and a client that disconnects ends its request span with an `aborted` event.
- Logs: Effect log records are exported with the trace and span ids of the fiber that wrote them. A failed procedure is logged once by a client interceptor: client errors at info, everything else at error with its cause.
- Metrics: pg-boss messaging metrics (`messaging.*`, `pgboss.queue.jobs`) and the HTTP client duration, exported every minute.
- AI calls record model, token usage and the organisation, chat, provider and model ids, never prompt or response content.
