title: End-To-End Tests
description: How the Playwright end-to-end suite and the integration tier are run, isolated, and extended.
---

The end-to-end suite proves that the application works against real infrastructure: a real database, real authorisation store, real object storage. Unit tests (`bun run test`) never touch the stack; the end-to-end suite always does. Each unit test file runs isolated in a pool of worker processes (`bun test --parallel`), so `mock.module` and DOM globals stay within their file.

## Runner

- Playwright Test on the host, Chromium only.
- Workspace package `apps/e2e` (`@orcai/e2e`).
- Browser locale `en`. Locators use roles and accessible names taken from the message catalogue through `fixtures/messages.ts`, never a repeated English literal; test ids only where no accessible name exists. See [Localisation](/docs/development/localisation).
- Traces and screenshots are kept on failure. Test timeout 30 seconds.
- Locally: Playwright's default worker count, no retries. On CI: two workers and one retry; flaky retries fail CI.

## Workflow

The suite runs against the checkout's own stack.

```bash title="Repository root"
bun run stack e2e                              # reset, then the whole suite
bun run e2e                                    # root alias
bun run stack e2e -- --grep auth               # one spec area
bun run stack e2e -- --ui                      # Playwright UI mode
bun run stack e2e --no-reset -- --grep smoke   # fast iteration on existing data
bun run stack e2e --no-integration             # Playwright only
bun run stack e2e --no-build                   # reuse the images already built
bun run stack e2e --pipeline                   # the pipeline specs, with workers
```

Everything after `--` is passed to Playwright. After Playwright, whatever its result, the run executes the [integration tier](#integration-tier) on the same stack; the run fails if either does. A full local run is `bun run stack e2e` followed by `bun run stack e2e --pipeline`; see [Pipeline Specs](#pipeline-specs).

<Callout title="A run wipes the stack's data" type="warn">
	A run that resets asks for confirmation first. `--yes` answers up front, and a caller without a terminal has to pass it. Unless you pass `--no-reset`, `bun run stack e2e` resets the stack first: it drops and recreates the `app` database, reapplies migrations and the SpiceDB schema, deletes all SpiceDB relationships, empties the object storage buckets, deletes the Qdrant collections, and flushes Valkey. Containers and `.env` are left in place, so a reset takes seconds. The reset refuses unless the database host is loopback, `S3_ENDPOINT` is the stack's own loopback SeaweedFS, the stack is named `orcai-*`, and nothing is listening on the app port. To keep your development data, run the suite against a second stack with `bun run stack --name <name>-e2e --env-file .env.e2e up`, then the same flags on `e2e`.
</Callout>

`bun run stack e2e` first installs the Chromium that the pinned `apps/e2e` Playwright expects into the shared Playwright cache; once it is there, the step is a no-op.

The application under test is the production images, the ones a Docker Compose deployment runs. Before the reset, `bun run stack e2e` builds the app and docs images (app and workers for `--pipeline`) with `docker buildx bake` from the build definitions in `docker-compose.yaml` and tags them `<stack>-app`, `<stack>-web`, and `<stack>-workers`. `--no-build` skips the build and fails when an image is missing. Playwright's `webServer` list first starts the mock inference server from `apps/e2e/fixtures/inference` on `E2E_INFERENCE_PORT`, then runs the app image on the `PORT` from the stack environment, then the docs image on `WEB_PORT`. Each container runs with `docker run --network host` and the stack environment as its env file, so it reaches the stack and the mock on loopback. The browser opens the app at `http://localhost:<PORT>`, the `BETTER_AUTH_URL` the run sets even when an older `.env` names `127.0.0.1`, because WebAuthn refuses an IP address as the passkey relying party; clients for `localhost` fall back to the 127.0.0.1 the servers bind. Each container is named after its image and removed when Playwright stops it, and `bun run stack e2e` removes leftovers before and after a run. The images run with `NODE_ENV=production`, so the run sets `BETTER_AUTH_RATE_LIMIT=false`: every request comes from loopback without a forwarded client IP and would share one rate limit. `bun run stack e2e` points the app's global OpenAI-compatible endpoint at the mock and names its models in `GENERAL_MODEL` and `EMBEDDING_MODEL`, so embeddings and chat titles never reach a real provider. `bun run stack e2e` points `WEB_INTERNAL_URL` at that docs site, so the assistant reads the real docs, and assistant specs compare against what the site serves. The mock always starts fresh and refuses to adopt an existing server. Because `reuseExistingServer` is enabled for the app and the docs site, a running `bun run stack web` is reused, and `bun run stack e2e --no-reset` reuses a `bun run stack dev` already listening on that port; `bun run stack e2e` then skips that image's build, and the dev server picks up code edits immediately. A reset refuses while an app is listening, because a running server caches the bootstrap status and owns the pg-boss schema it created on start; stop the dev server first or pass `--no-reset`.

## Seed And Isolation

There is no seed command. A Playwright `setup` project holds one spec that initialises the reset instance through the first-run UI at `/init` with a well-known admin whose credentials and instance organisation are fixed constants. If the instance is already initialised, the spec skips itself with a visible reason. Every other project depends on `setup`, so a full run always exercises first-run setup and always has the well-known admin available.

The reset happens once per run. Beyond the well-known admin, every Playwright worker creates its own organisations and users through the public API, named by worker index, and specs mutate only data inside their own worker's organisations. Users are created through the Better Auth sign-up endpoint and then given a role through the membership procedure. Creating an organisation requires the instance-admin role, so the well-known admin creates every worker organisation and becomes an admin member of each. It does not need an active organisation to perform that instance-scoped action, but membership and invitation procedures act on the active organisation, so the fixtures open a separate well-known admin session per created organisation, activate that organisation on it, and invite and remove members through it. The shared well-known admin session keeps the instance organisation active. Fixture setup still exercises the same paths the interface does. Specs that need instance-level state live in `apps/e2e/tests/instance/`; that project runs serially and completes before the parallel specs start.

## Integration Tier

Modules that need real PostgreSQL, SpiceDB, or Valkey are tested through their interface in `*.integration.ts` files, alongside the unit tests. `bun test` does not discover that suffix, so `bun run test` stays free of infrastructure.

```bash title="Repository root"
bun run test:integration                                        # every integration file
bun run stack exec -- bun test ./packages/spice-db/test/schema.integration.ts   # one file
```

`bun run test:integration` finds every `*.integration.ts` under `apps` and `packages` and runs them with `bun test --parallel` through `bun run stack exec`, so they get the stack environment. The tier needs a migrated stack, nothing else; it runs no reset.

Tests create their own organisations and users under unique ids, so they coexist with development data and with each other. Bootstrap counts any user or organisation as an initialised instance, so a test row on a fresh stack would lock first-run setup; `integrationRuntime()` therefore fails until the instance is initialised through `/init` or a `bun run stack e2e` run.

`@orcai/testing` holds the shared helpers:

| Helper | Provides |
| --- | --- |
| `integrationRuntime()` | A `ManagedRuntime` over `IntegrationLive`, the app's `DrizzleLive` and `SpiceDbLive` layers built from the stack environment, disposed after the file's last test. |
| `createUser({ role })` | A user row with a unique email, instance role `user` unless given. |
| `createOrganization({ members })` | An organisation with a unique slug whose members hold their role in both the `member` table and SpiceDB, and the `zedToken` of that write. |

`packages/spice-db/test/schema.integration.ts` checks the SpiceDB schema: it writes a fixed set of relationships under per-run ids and asserts which permissions they grant and deny against the stack's applied schema.

## Fixtures

Specs import `test` and `expect` from `apps/e2e/fixtures/index.ts` and get their data through fixtures rather than direct database writes.

| Fixture | Scope | Provides |
| --- | --- | --- |
| `org` | worker | The worker's organisation: `id`, `slug`, `name`, and `users[role]` for `admin`, `manager`, `member`, and `viewer`, each with `email`, `password`, and `id`, plus per-role storage states obtained by HTTP sign-in. |
| `pageAs(role)` | test | A page already signed in as that role. |
| `api.as(role)` | test | A typed oRPC client against `/api/rpc`, built from the shared contracts. `api.asWellKnownAdmin()` covers instance-level calls. |
| `orgs.create(name)` | worker | An additional organisation owned by the worker, for seam tests that need two. |
| `outbox.latestFor(email, type)` | test | The newest link for an address from the notification outbox table, for invitation and password-reset flows. |
| `inference` | worker | A mock OpenAI-compatible inference server on an ephemeral port, from `fixtures/inference/fixture.ts`. Its URL is a valid provider endpoint; it records every request and can script replies and failures. |

Out of scope for the suite: email delivery, real AI endpoints, and OCR. Background workers run only for the pipeline specs.

## Pipeline Specs

The specs in `apps/e2e/tests/pipeline/` cover upload, processing, indexing, search, and citation with the real background workers. Only `bun run stack e2e --pipeline` runs them, and only that run starts the workers: it sets `E2E_PIPELINE`, on which the Playwright configuration selects the `setup` and `pipeline` projects and runs the workers image in place of the docs site, ready once the workers log that they started. `bun run stack e2e --pipeline` sets `WORKER_POLLING_INTERVAL_SECONDS=0.5`, so a document is ready within seconds.

Every other run has no workers, so no pg-boss queue exists: queueing processing fails and an uploaded document ends up failed with kind `other`, which the other specs rely on. A pipeline run leaves its queues behind, so reset before the next run of the rest of the suite.

Pipeline documents are txt or md, so extraction needs no OCR. Their embeddings come from the mock inference server, whose `EMBEDDING_DIMENSIONS` matches the stack's Qdrant collection; image descriptions are not exercised. `fixtures/pipeline/repository.ts` creates a repository holding one uploaded document and waits through `block.readiness` until nothing in it is being prepared.

## Slices

A slice is one spec area owned by one contributor or agent. A slice owns `apps/e2e/tests/<area>/` and may add fixtures under `apps/e2e/fixtures/<area>/`. Everything else in `apps/e2e` belongs to the foundation: the Playwright configuration, `fixtures/index.ts`, and the core fixtures for authentication, authorization, API access, constants, forms, navigation, and the outbox. The same applies to `scripts/stack.ts` and these documentation pages. A slice that needs one of those changed stops and reports instead of editing it.

Rules for working on a slice:

- Reset before a full run; use `--no-reset` only while iterating.
- Mutate data only inside your own worker's organisations.
- Finish with `bun run stack e2e -- --grep <area>` passing.
- Pin a defect the app has today with `test.fail()` and a comment; assert the intended behaviour, never the defect.

Each area under `apps/e2e/tests/<area>/` owns its specs and may add area
fixtures. The Playwright configuration, core fixtures, and stack tooling are
foundation files shared by every area; coordinate before changing them.

## Continuous Integration

GitHub Actions runs the suite in parallel with `validate`, split across three shard jobs with Playwright's `--shard` and a fourth job for the pipeline specs. An `e2e images` job first writes a stack environment, builds the app, docs, and workers images with `bun run stack build`, caching their layers in the GitHub Actions cache, and uploads the images as an artifact kept for a day. The images carry no stack values, so each shard job loads them, installs Chromium with the pinned `apps/e2e` Playwright, starts its own stack, which writes its own environment, runs `bun run stack e2e --yes --no-build` with its arguments (`-- --shard=<i>/3`, or `--pipeline`), and uploads its failure artifacts for seven days. Shard 1 also runs the integration tier; the other jobs pass `--no-integration`. The `setup` and `instance` projects are dependencies, so every shard runs them before its share of the rest; the pipeline job runs `setup` only. The required `e2e` job passes when the image job and every shard passed.

Pull requests that only change docs content (`apps/web/content`), `LICENSE`, or Markdown outside `apps/app`, `apps/workers`, and `packages` skip the shards; `e2e` still reports success. Pushes to `main` always run the full suite.

Worker-local inference settings reset before and after every test, including
failed tests; other workers keep their own scenarios. Well-known-admin browser
pages sign in independently of the admin API client. Changing organisation on
one session does not change the other.

Unknown stack flags before `--` fail with a clear error. Everything after `--`
is preserved for the delegated command.

The documentation build prerenders on a free preview port when port 3001, the
docs site's own port, is occupied, so another local server does not block
`bun run ci`.
