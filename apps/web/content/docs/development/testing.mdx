---
title: End-to-end tests
description: How the Playwright end-to-end suite and the integration tier are run, isolated, and extended.
---

The end-to-end suite proves that the application works against real infrastructure: a real database, a real authorisation store and real object storage. Unit tests (`bun run test`) never touch the stack, and the end-to-end suite always does. Each unit test file runs isolated in a pool of worker processes (`bun test --parallel`), so `mock.module` and DOM globals stay within their file.

App unit tests that call the API replace `@/lib/orpc/orpc` with `scriptedOrpc` from `@/lib/testing/scripted-orpc`. It keeps the app's query utilities and answers only the procedures the test scripts, so an unscripted call fails with its name. Chat message parts come from the builders in `@/lib/ai/test-parts`, which check each part against the stored part schema.

## Runner

- Playwright Test on the host, Chromium only.
- Workspace package `apps/e2e` (`@orcai/e2e`).
- Browser locale `en`. Locators use roles and accessible names taken from the message catalogue through `fixtures/messages.ts`, never a repeated English literal, and test ids only where no accessible name exists. See [Localisation](/docs/development/localisation).
- Traces and screenshots are kept on failure. Test timeout 30 seconds.
- Playwright's default worker count and no retries locally. Two workers and one retry on CI, where a flaky retry fails the run.

## Workflow

The suite runs against the checkout's own stack.

```bash title="Repository root"
bun run stack e2e                              # reset, then the whole suite
bun run e2e                                    # root alias
bun run stack e2e -- --grep auth               # one spec area
bun run stack e2e -- --ui                      # Playwright UI mode
bun run stack e2e --no-reset -- --grep smoke   # fast iteration on existing data
bun run stack e2e --no-integration             # Playwright only
bun run stack e2e --no-build                   # reuse the images already built
bun run stack e2e --pipeline                   # the pipeline specs, with workers
```

Everything after `--` is passed to Playwright. After Playwright, whatever its result, the run executes the [integration tier](#integration-tier) on the same stack, and the run fails if either does. A full local run is `bun run stack e2e` followed by `bun run stack e2e --pipeline`, see [Pipeline specs](#pipeline-specs).

<Callout title="A run wipes the stack's data" type="warn">
	A run that resets asks for confirmation first. `--yes` answers up front, and a caller without a terminal has to pass it. Unless you pass `--no-reset`, `bun run stack e2e` resets the stack first: it drops and recreates the `app` database, reapplies migrations and the SpiceDB schema, deletes all SpiceDB relationships, empties the object storage buckets, and deletes the Qdrant collections. Containers and `.env` are left in place, so a reset takes seconds. The reset refuses unless the database host is loopback, `S3_ENDPOINT` is the stack's own loopback SeaweedFS, the stack is named `orcai-*`, and nothing is listening on the app port. To keep your development data, run the suite against a second stack with `bun run stack --name <name>-e2e --env-file .env.e2e up`, then the same flags on `e2e`.
</Callout>

`bun run stack e2e` first installs the Chromium that the pinned `apps/e2e` Playwright expects into the shared Playwright cache, and once it is there the step is a no-op.

The application under test is the production images, the ones a Docker Compose deployment runs. Before the reset, `bun run stack e2e` builds the app and docs images (app and workers for `--pipeline`) with `docker buildx bake` from the build definitions in `docker-compose.yaml` and tags them `<stack>-app`, `<stack>-web`, and `<stack>-workers`. `--no-build` skips the build and fails when an image is missing.

Playwright's `webServer` list first starts the mock inference server from `apps/e2e/fixtures/inference` on `E2E_INFERENCE_PORT`, then runs the app image on the `PORT` from the stack environment, then the docs image on `WEB_PORT`. Each container runs with `docker run --network host` and the stack environment as its env file, so it reaches the stack and the mock on loopback. The browser opens the app at `http://localhost:<PORT>`, the `BETTER_AUTH_URL` the run sets even when an older `.env` names `127.0.0.1`, because WebAuthn refuses an IP address as the passkey relying party. Clients for `localhost` fall back to the 127.0.0.1 the servers bind. Each container is named after its image and removed when Playwright stops it, and `bun run stack e2e` removes leftovers before and after a run. The images run with `NODE_ENV=production`, and every request comes from loopback without a forwarded client IP and would share one rate limit, so the run sets `BETTER_AUTH_RATE_LIMIT=false`. The `setup` project saves the mock as the instance's embedding endpoint, so embeddings never reach a real provider. `bun run stack e2e` points `WEB_INTERNAL_URL` at that docs site, so the OrcAI Assistant reads the real docs, and Assistant specs compare against what the site serves. The mock always starts fresh and refuses to adopt an existing server.

The app container's standard output, where its logs go, does not reach the console: each run writes it to `apps/e2e/logs/app.log`, cleared at the start of the run, and errors the app prints still show in the console. When Playwright fails, `bun run stack e2e` also saves the PostgreSQL and SpiceDB logs there (`postgres.log`, `spicedb.log`, `spicedb-database.log`), so a slow or stalled run can be traced to the app or the databases.

Because `reuseExistingServer` is enabled for the app and the docs site, a running `bun run stack web` is reused, and `bun run stack e2e --no-reset` reuses a `bun run stack dev` already listening on that port. `bun run stack e2e` then skips that image's build, and the dev server picks up code edits immediately. A reset refuses while an app is listening, because a running server caches the bootstrap status and owns the pg-boss schema it created on start. Stop the dev server first or pass `--no-reset`.

## Seed and isolation

There is no seed command. A Playwright `setup` project holds one spec that initialises the reset instance through the first-run UI at `/init` with a well-known admin whose credentials and instance organisation are fixed constants. The spec then lands on the instance **Settings** page and saves the mock inference server on `E2E_INFERENCE_PORT` as the embedding endpoint, with the model `e2e-mock-embedding` and its 1024 dimensions. `bun run stack e2e` seeds no embedding setting of its own. If the instance is already initialised, the spec skips itself with a visible reason. A last setup spec marks the initial tour skipped for the well-known admin. Every other project depends on `setup`, so a full run always exercises first-run setup and always has the well-known admin available.

The reset happens once per run. Beyond the well-known admin, every Playwright worker creates its own organisations and users through the public API, named by worker index, and specs mutate only data inside their own worker's organisations. Users are created through the Better Auth sign-up endpoint and then given a role through the membership procedure. Every fixture user has skipped the initial tour, whose modal card would cover the app home. A spec of the tour itself asks `signUpInvited` or `createAccountUser` for `initialTour: "unseen"`.

Creating an organisation requires the instance-admin role, so the well-known admin creates every worker organisation and becomes an admin member of each. It does not need an active organisation to perform that instance-scoped action, but membership and invitation procedures act on the active organisation, so the fixtures open a separate well-known admin session per created organisation, activate that organisation on it, and invite and remove members through it. The shared well-known admin session keeps the instance organisation active. Well-known admin browser pages sign in independently of the admin API client, so changing organisation on one session does not change the other. Fixture setup still exercises the same paths the interface does. Specs that need instance-level state live in `apps/e2e/tests/instance/`, and that project runs serially and completes before the parallel specs start. With `E2E_NO_INSTANCE` set, the configuration leaves the `instance` project out and the parallel specs depend on `setup` alone.

## Integration tier

Modules that need real PostgreSQL or SpiceDB are tested through their interface in `*.integration.ts` files, alongside the unit tests. `bun test` does not discover that suffix, so `bun run test` stays free of infrastructure.

```bash title="Repository root"
bun run test:integration                                        # every integration file
bun run stack exec -- bun test ./packages/spice-db/test/schema.integration.ts   # one file
```

`bun run test:integration` finds every `*.integration.ts` under `apps` and `packages` and runs them with `bun test --parallel` through `bun run stack exec`, so they get the stack environment, and writes per-test durations to `reports/integration.xml`. The tier needs a migrated stack and nothing else, and it runs no reset.

Tests create their own organisations and users under unique ids, so they coexist with development data and with each other. Bootstrap counts any user or organisation as an initialised instance. Because a test row on a fresh stack would lock first-run setup, `integrationRuntime()` fails until the instance is initialised through `/init` or a `bun run stack e2e` run.

`@orcai/testing` holds the shared helpers. It depends only on the database and SpiceDB packages, so any package can test with it:

| Helper | Provides |
| --- | --- |
| `integrationRuntime(layer)` | A `ManagedRuntime` over `IntegrationLive`, the app's `DrizzleLive` and `SpiceDbLive` layers built from the stack environment, and the file's own `layer`. It is built before the file's first test, so no test carries the build, and disposed after its last. |
| `createUser({ role })` | A user row with a unique email, instance role `user` unless given. |
| `createOrganization({ members })` | An organisation with a unique slug whose members hold their role in both the `member` table and SpiceDB, and the `zedToken` of that write. |
| `holdLock(lock)`, `awaitLockWaiters(on, count)` | Hold a lock in a transaction of its own, and wait until a number of statements wait on it, given as an advisory lock from `lockSpaces` or a statement pattern. |
| `rolledBack(effect)` | Runs an effect in a transaction that is rolled back, for code that drains tables other files write to. |
| `rejection(promise)`, `reasonOf(promise)` | What a call rejects with, or the `reason` of it. |

Helpers that need more of the stack live with their package:

| Helper | Provides |
| --- | --- |
| `IsolatedPgBossLive()` from `@orcai/pg-boss/testing` | A pg-boss in a schema of the file's own with every queue of the queue table, dropped after the file. No other file sees or wakes its jobs. A file that runs workers with `runWorkers` passes a pg-boss `TestClock` and moves its time on with `setTime`, so retry delays and expiry pass without waiting. |
| `testEmbeddingIndex()` and `IsolatedEmbeddingIndexLive()` from `@orcai/qdrant/testing` | An embedding index with its own settings table and collection prefix. |
| `appIntegration()` in `apps/app/src/lib/testing/app-integration.ts` | The app's layers on an isolated pg-boss, with session fixtures and `caller(zedToken)`, which runs procedures as actors with the latest zed token. `organizationByRole()` gives one signed-in member per organisation role and the All Members group, and `outcomesByRole` records whether each role's call is allowed or which error it fails with, with the responses of the allowed calls. |

`packages/spice-db/test/schema.integration.ts` checks the SpiceDB schema. It writes a fixed set of relationships under per-run ids and asserts which permissions they grant and deny against the stack's applied schema.

Integration tests await a call before asserting on its outcome. `rejection(promise)` gives what the call rejects with, and `reasonOf(promise)` gives that error's `reason`. Both come from `@orcai/testing`. Under `bun test`, the matchers `.rejects`, `.resolves` and `expect(async ...)` can leave a SpiceDB response unread until the call's deadline ([oven-sh/bun#39796](https://github.com/oven-sh/bun/issues/39796)). The Biome plugin `packages/testing/await-before-expect.grit` therefore rejects them in `*.integration.ts` files.

## Fixtures

Specs import `test` and `expect` from `apps/e2e/fixtures/index.ts` and get their data through fixtures rather than direct database writes.

| Fixture | Scope | Provides |
| --- | --- | --- |
| `org` | worker | The worker's organisation: `id`, `slug`, `name`, and `users[role]` for `admin`, `manager`, `member`, and `viewer`, each with `email`, `password`, and `id`, plus per-role storage states obtained by HTTP sign-in. |
| `pageAs(role)` | test | A page already signed in as that role. |
| `pageForSession(session)` | test | A page carrying a session captured earlier, for users made outside the worker organisation. |
| `newContext(options)` | test | A browser context, English unless the options say otherwise, closed after the test. |
| `api.as(role)` | test | A typed oRPC client against `/api/rpc`, built from the shared contracts. `api.asWellKnownAdmin()` covers instance-level calls. |
| `orgs.create(name)` | worker | An additional organisation owned by the worker, for seam tests that need two. |
| `outbox.latestFor(email, type)` | test | The newest link for an address from the notification outbox table, for invitation and password-reset flows. |
| `inference` | test | The worker's mock OpenAI-compatible inference server from `@orcai/ai/testing`, on an ephemeral port. Its URL is a valid provider endpoint, and it records every request and can script replies and failures. `fixtures/inference/requests.ts` reads the recorded requests. |

Every page from these fixtures fails its test when it throws an uncaught error, and React reports a hydration mismatch that way too. The test fails at its end with every such error and the address of the page that threw it. Specs get no `browser` or `playwright` fixture, and lint refuses Playwright's browser launchers and `.browser()` in specs, so `newContext` is the only way to open another context.

The `inference` fixture's scripted replies and failures reset before and after every test that uses it, including failed tests, and other workers keep their own scenarios. The mock's own contract tests are unit tests in `packages/ai/test`.

`fixtures/users.ts` creates the users a test may change: `createUser` for one in no organisation, `createMember` for a member of the caller's organisation, and `addMember` adds an existing user to another organisation. `open` and `submitForm` wait until the page has hydrated; after a reload `open` did not make, call `awaitHydration` before interacting.

The suite does not cover email delivery or real AI endpoints. Background workers run only for the pipeline specs, and only those run OCR, in the workers image.

## Pipeline specs

The specs in `apps/e2e/tests/pipeline/` cover upload, preparation, indexing, search, and citation with the real background workers. Only `bun run stack e2e --pipeline` runs them, and only that run starts the workers. It sets `E2E_PIPELINE`, and with it the Playwright configuration selects the `setup` and `pipeline` projects and runs the workers image in place of the docs site, ready once the workers log that they started. `bun run stack e2e --pipeline` sets `WORKER_POLLING_INTERVAL_SECONDS=0.5`, so an asset is ready within seconds.

Every other run has no workers, so only the data export queues the app creates exist. Queueing preparation fails, and an uploaded asset ends up failed with kind `other`, which the other specs rely on. A pipeline run leaves its queues behind, so reset before the next run of the rest of the suite.

Most pipeline assets are txt or md files. The extraction specs upload PDFs that Chromium prints, with text in a figure, so the workers image reads them with Tesseract. Their embeddings come from the mock inference server that the `setup` project saved as the embedding endpoint. Image descriptions are not exercised. `fixtures/pipeline/repository.ts` creates a repository holding one uploaded asset and waits through `block.readiness` until nothing in it is being prepared.

## Slices

A slice is one spec area owned by one contributor or agent. A slice owns `apps/e2e/tests/<area>/` and may add fixtures under `apps/e2e/fixtures/<area>/`. Everything else in `apps/e2e` belongs to the foundation: the Playwright configuration, `fixtures/index.ts`, and the core fixtures for authentication, authorisation, API access, constants, forms, navigation, and the outbox. The same applies to `scripts/stack.ts` and these documentation pages. A slice that needs one of those changed stops and reports instead of editing it.

Rules for working on a slice:

- Reset before a full run, and use `--no-reset` only while iterating.
- Mutate data only inside your own worker's organisations.
- Finish with `bun run stack e2e -- --grep <area>` passing.
- Pin a defect the app has today with `test.fail()` and a comment, and assert the intended behaviour, never the defect.

## Continuous integration

GitHub Actions runs the suite in parallel with `validate`, split across three shard jobs with Playwright's `--shard`, a job for the instance specs, and one for the pipeline specs. An `e2e images` job first writes a stack environment, builds the app, docs, and workers images with `bun run stack build`, caching their layers in the GitHub Actions cache, and uploads the images as an artifact kept for a day. The images carry no stack values, so each shard job loads them, installs Chromium with the pinned `apps/e2e` Playwright, starts its own stack, which writes its own environment, runs `bun run stack e2e --yes --no-build` with its arguments (`-- --shard=<i>/3`, `-- --project=instance`, or `--pipeline`), and when it fails uploads the Playwright report, the test results, and `apps/e2e/logs` for seven days. Shard 1 also runs the integration tier, and the other jobs pass `--no-integration`. Playwright runs a dependency project in full on every shard, so the serial `instance` project runs once, in a job of its own, and the shards set `E2E_NO_INSTANCE`. Every job runs `setup` first. Every job uploads `reports/`, the JUnit files of Playwright (`e2e.xml`) and of the integration tier (`integration.xml`) with per-test durations, kept for 30 days. The required `e2e` job passes when the image job and every shard passed.

Pull requests that only change docs content (`apps/web/content`), `LICENSE`, or Markdown outside `apps/app`, `apps/workers`, and `packages` skip the shards, and `e2e` still reports success. Pushes to `main` always run the full suite.
